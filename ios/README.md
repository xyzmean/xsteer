# Xsteer под iOS

Клиент xsteer для iPhone и iPad: приложение-контейнер плюс расширение
`NEPacketTunnelProvider`, внутри которого работает та же половина на Go, что и на настольных
системах. Протокол, шифрование и рукопожатие не переписаны — часть на Swift занимается только
тем, что принадлежит платформе.

**Ничего из этого ещё не запускалось на живом устройстве.** Собирается, проверяется тестами,
типизируется под `ios/arm64` — но ни одного пакета через настоящий телефон не прошло. Пока это
так, здесь об этом написано.

## Сначала о главном: чем это можно поставить

Тоннелю на iOS нужно право `com.apple.developer.networking.networkextension` со значением
`packet-tunnel-provider`. Другого способа получить пакеты системы на iOS нет: ни сырых сокетов,
ни своего драйвера, ни обхода. Это право открывается самообслуживанием **только платному
участию** в программе разработчика Apple ([документация
Apple](https://developer.apple.com/documentation/xcode/configuring-network-extensions)).

**Бесплатная личная команда его не получает, и AltStore тут не помогает.** Лучшее доказательство —
сам SideStore, форк AltStore: чтобы поднять тоннель без платного участия, его авторам пришлось
выпустить ОТДЕЛЬНОЕ приложение в App Store (`LocalDevVPN`), подписанное Apple и уже несущее это
право ([SideStore](https://github.com/SideStore/SideStore)). Если бы подпись бесплатным Apple ID
позволяла тоннель, этот обход был бы не нужен. Заодно про бесплатный Apple ID: три приложения
одновременно, десять разных за неделю, срок семь дней
([документация SideStore](https://docs.sidestore.io/docs/faq)).

Отсюда три пути, и выбирать между ними приходится не по удобству:

| путь | Mac | платное участие | срок сборки |
|---|---|---|---|
| Actions плюс своя страница установки | не нужен | нужно | 365 дней |
| Actions плюс TestFlight | не нужен | нужно | 90 дней |
| Xcode на своём Mac | нужен | нужно | 7 или 365 дней |

Платное участие обязательно во всех трёх. Разница только в том, чем ставить и как часто
пересобирать.

**Здесь настроен первый.** Своего Mac не нужно нигде: собирает бегунок macOS в GitHub Actions
(для открытых хранилищ они бесплатны, а `xsteer` открыт), подпись автоматическая по ключу
доступа, а готовое приложение выкладывается на GitHub Pages вместе со страницей, с которой оно
ставится нажатием ссылки прямо на телефоне. App Store Connect в этом пути не участвует вовсе.

Второй путь тоже настроен и включается тем же заданием: внутренним испытателям TestFlight
отдаёт сборку через минуты после отправки, без проверки Apple, и она живёт 90 дней
([App Store Connect](https://www.developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview)).

Сертификат при этом создаётся без Mac, но и этого не потребуется: с ключом доступа к App Store
Connect Xcode на бегунке заводит сертификат и профили сам, включая право на тоннель и список
устройств.

## Что нужно один раз

1. Платное участие в программе разработчика Apple.
2. **Внести телефон в список устройств.** `developer.apple.com` → Devices → плюс, тип iOS,
   идентификатор устройства. Где его взять без Mac: подключите телефон, откройте в браузере
   `Настройки → Основные → Об этом устройстве`, нажмите и подержите строку с серийным номером —
   либо посмотрите в Finder, iTunes или любом приложении вроде «Apple Devices». **Без этого шага
   установка со страницы молча не начинается** — это самая частая причина, по которой ссылка
   «ничего не делает».
3. Ключ доступа к App Store Connect: **Users and Access → Integrations → App Store Connect
   API** → создать ключ с ролью App Manager. Скачивается один раз, файлом `AuthKey_XXXX.p8`.
4. Четыре значения в **Settings → Secrets and variables → Actions** хранилища:

   | ключ | что это |
   |---|---|
   | `ASC_KEY_P8_BASE64` | содержимое `.p8`, закодированное base64 |
   | `ASC_KEY_ID` | идентификатор ключа, десять символов |
   | `ASC_ISSUER_ID` | идентификатор издателя, из той же страницы |
   | `IOS_TEAM_ID` | идентификатор команды, десять символов |

5. Включить страницы: **Settings → Pages → Source → GitHub Actions**. Если у страницы своё
   доменное имя, положите его в переменную хранилища `PAGES_BASE` — иначе адрес выводится как
   `https://<владелец>.github.io/<хранилище>`.

Дальше: **Actions → iOS → Run workflow**, выбрать `page`. Сборка кладёт `.ipa` в артефакты
прогона, а страницу собирает и выкладывает отдельное задание **Pages** — оно запускается само
следом за успешной сборкой. Через полчаса по адресу страниц появится страница с кнопкой
«Установить»; откройте её на телефоне **в Safari** (другие браузеры ссылку установки не
обрабатывают) и нажмите кнопку. После установки один раз доверьте разработчику в
`Настройки → Основные → VPN и управление устройством`.

Страница одна на все платформы, и выкладывает её только задание **Pages**. Так сделано потому,
что выкладка заменяет сайт хранилища ЦЕЛИКОМ: публикуй каждая сборка своё, они стирали бы работу
друг друга, и страница iOS исчезала бы при первом же коммите в Android.

Номер сборки — номер прогона, и это не мелочь: телефон ставит поверх уже стоящего только то, у
чего номер выше.

Выбор `testflight` в том же задании отправляет сборку в TestFlight вместо страницы. Выбор `none`
и любой обычный коммит просто проверяют, что всё компилируется, — подписывать для этого нечего.

Кодировать `.p8` в base64 можно где угодно, Mac для этого не нужен:

```sh
base64 -w0 AuthKey_XXXXXXXXXX.p8
```

## Сборка на своём Mac

```sh
brew install xcodegen
cp ios/Support/local.xcconfig.example ios/Support/local.xcconfig
# впишите в него свой DEVELOPMENT_TEAM
ios/build-framework.sh          # gomobile bind -> mobile/build/Xsteer.xcframework
cd ios && xcodegen generate && open Xsteer.xcodeproj
```

`project.yml` вместо готового `.xcodeproj` намеренно: файл проекта Xcode — это машинный plist, в
котором каждая ссылка есть двадцатичетырёхзначный идентификатор. Его нельзя ни прочитать глазами,
ни разумно слить при расхождении, а написанный руками он ломается молча.

## Как это устроено

```
mobile/                      часть на Go, собирается в Xsteer.xcframework
  go.mod                     ОТДЕЛЬНЫЙ модуль — см. ниже
  device.go                  tun.Device поверх вызовов из Swift
  mobile.go                  плоское API, которое переносит gomobile
ios/
  App/Sources/               приложение: настройка в системе, кнопка, состояние
  Tunnel/Sources/            расширение: пакеты, настройки туннеля, сторож пути
  build-framework.sh         gomobile bind (только на macOS)
  project.yml                описание проекта для XcodeGen
contrib/make-icons.py        иконка приложения и картинки страницы (общая с Android)
site/                        заготовки страницы установки, общие с Android
```

Страница установки собирается из заготовок в `site/`: метки `@ИМЯ@` подставляет
`site/build-site.py`, потому что адреса зависят от того, где страница лежит. Заготовки держатся
файлами, а не строками внутри описания сборки, чтобы их можно было прочитать глазами; сборщик
проверяет, что незакрытых меток не осталось, — иначе страница молча не работала бы, указывая
ссылкой на `@MANIFEST@`. Собрать и посмотреть её можно и без бегунка:

```sh
python3 site/build-site.py --out /tmp/site --base https://example.github.io/xsteer
```

Границу проводит один принцип: **на Swift остаётся только то, что принадлежит платформе.**
Настройки туннеля (адрес, маска, маршруты, резолвер, MTU), чтение и запись пакетов через
`packetFlow` и извещения о смене сети. Разбор настройки, ключи, протокол, шифрование,
рукопожатие и согласование MTU — целиком в Go, и ни одна строка этого не повторяется на Swift.
Иначе у двух половин появились бы два мнения о том, что такое правильная настройка, и они
разошлись бы при первой же правке формата.

### Почему мост — отдельный модуль Go

`gomobile bind` требует `golang.org/x/mobile` в графе зависимостей того модуля, в котором он
запущен, а сам `golang.org/x/mobile` требует Go 1.26. Положить его в модуль движка значило бы
поднять нижнюю границу Go для всех, кто собирает xsteer на роутер или на сервер, — ради
инструмента, который нужен только сборке под iOS и только на macOS. Заодно туда приехали бы
`x/mod`, `x/sync` и `x/tools` и обновление `x/sys`, то есть чужие зависимости в модуль, где вся
сеть написана на стандартной библиотеке.

Цена решения одна и о ней стоит помнить: **`go test ./...` в корне этот модуль не видит**,
вложенные модули из перебора исключаются. Его проверки гоняются отдельным шагом в `ci.yml`, и
запускать их руками надо из каталога: `cd mobile && go test ./...`.

Движок берётся через `replace` из этого же дерева, а не из сети: мост и протокол правятся вместе,
и версия из сети означала бы, что мост собран не с тем кодом, который рядом лежит.

### Три решения, которые стоит знать

**Транспорт только режимом потока.** Обычный транспорт xsteer подделывает TCP: заголовок
настоящий, семантика датаграммная. Для этого нужен сырой сокет, а в песочнице iOS его нет и не
будет. Поэтому `Stream: true` прошит, а не выставляется настройкой: это следствие платформы, а не
выбор. Цена названа в шапке `wire/stream.go` — внутренний TCP едет поверх внешнего.

**MTU не больше 1439.** Путь данных читает пакеты окном ровно такого размера и признака усечения
не имеет, поэтому пакет крупнее был бы выброшен целиком, а снаружи это выглядело бы как «мелкое
ходит, крупное пропадает». В настройках расширения стоит то же число, что в конфигурации, и
никогда больше; сколько выброшено — видно в счётчике «слишком крупные».

**Склейка исходящих пакетов живёт на Swift, а не в Go.** Соблазн накапливать в Go и отдавать по
`tun.Device.Flush` велик, потому что переход через границу gomobile стоит около микросекунды. Но
входящий путь режима потока `Flush` не зовёт **вообще** — значит последний пакет всплеска пролежал
бы в буфере навсегда, если человек открыл одну страницу и замолчал. Поэтому признак конца
всплеска берётся у платформы: пакеты копятся и уходят одним `writePackets` на следующем витке
очереди.

### Чего у расширения нет

Памяти около пятнадцати мегабайт на весь процесс — отсюда очередь на 512 пакетов вместо 4096,
как на Linux. Запуск процессов невозможен, поэтому ни `ip`, ни `nft` не зовутся: клиент
поднимается с `Managed: true`, и всю системную обвязку делает `NEPacketTunnelNetworkSettings`.
Своё слежение за сетью выключено (`NoNetWatch`): там, где нет netlink, оно опрашивает адрес
выхода раз в пять секунд, а внутри расширения адресом источника ядро может назвать адрес самого
туннеля — и опрос решал бы, что сеть сменилась, каждые пять секунд. Правду сообщает
`NWPathMonitor`.

## Настройка

Та же, что у настольной половины: текст с разделами `Interface` и `Peer` либо одна строка
`xs://`. Разбирает её `conf.Parse` в Go, теми же проверками и с теми же отказами, что в консоли.

```ini
[Interface]
PrivateKey = <свой приватный ключ>
Address = 10.77.0.2/24
MTU = 1400
DNS = 1.1.1.1

[Peer]
PublicKey = <публичный ключ хаба>
AllowedIPs = 0.0.0.0/0
Endpoint = hub.example.com:443
```

Имя хаба здесь разрешается в адрес перед разбором: движок принимает только литерал IPv4, а
человек почти всегда пишет имя. Адрес IPv6 отвергается прямо — движок несёт только IPv4.

Пару ключей приложение умеет создавать само, на экране настройки.

## Что проверено и чем

`cd mobile && go test ./...` — 29 проверок: пустая очередь отвечает `ErrAgain`, а не нулём и не отказом;
пакет, не влезший в буфер, выбрасывается целиком и попадает в свой счётчик; переполнение очереди
теряет и считает, но не блокирует; `WaitRead` по истечении срока возвращает «нет» без ошибки, а
ошибку вызывающий счёл бы смертельной; запись отдаёт пакет до всякого `Flush`; семейство адресов
выводится из версии в первом полубайте, а не-IP отбрасывается; предела размера на записи нет;
чтение и запись из разных горутин по одному устройству; MTU зажимается до потолка; отказ разбора
доходит до человека тем же текстом, что в консоли; литерал адреса не переписывается, а IPv6
отвергается с объяснением.

Часть на Swift тестами не покрыта и на устройстве не запускалась.
